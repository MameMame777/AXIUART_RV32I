## Bug #6: Register Read/Write Pulse Confusion

### Symptom
- R0 register written with value 0x0A
- Value corrupted to 0x00 before ST instruction executed
- LED displayed 0x00 instead of expected 0x0A

### Root Cause
**File**: [rtl/register_block/Register_Block.sv](../rtl/register_block/Register_Block.sv)

Single pulse signal (`cpu_reg_write_pulse`) was used for two distinct operations:
1. **Read operation**: Writing CPU_REG_INDEX to select register for reading
2. **Write operation**: Writing CPU_REG_DATA to update register value

When CPU_REG_INDEX was written to read R0, the pulse incorrectly triggered a register write, corrupting R0 to 0x00.

### Solution
Separated control signals into two distinct pulses:

1. **`cpu_reg_read_pulse_set`** - Triggered by CPU_REG_INDEX write
   - Latches register index
   - Does NOT modify register contents
   
2. **`cpu_reg_write_pulse`** - Triggered by CPU_REG_DATA write
   - Actually writes to register file
   - Requires previous read pulse to set index

**Modified Files**:
- [rtl/register_block/Register_Block.sv](../rtl/register_block/Register_Block.sv)
  - Lines 139, 472-473, 550-551, 628-647, 742
- [rtl/cpu/td4cpu_core.sv](../rtl/cpu/td4cpu_core.sv)
  - Lines 243-260, 599

### Validation
✅ Test 1 PASSED - ST to LED MMIO (LED=0xA)  
✅ Test 2 PASSED - LD from LED MMIO (R0=0xA)

## Bug #7: Test Address Calculation Errors

### Symptom
Tests 3-5 failed with incorrect LED values:
- Test 3: Expected LED=0x01, got 0x00
- Test 4: Expected LED=0xFF, got 0x00
- Test 5: Expected LED=0x03, got 0x00

Waveform analysis revealed ST instructions wrote to RAM address 0x0044 instead of LED MMIO address 0x1044.

### Root Cause
**File**: [sim/tests/axiuart_cpu_mmio_led_test.sv](../sim/tests/axiuart_cpu_mmio_led_test.sv)

Tests used simplified address construction:
```systemverilog
LDI R1, #0x44  // Only sets lower 9 bits
```

This created address 0x0044 (RAM) instead of 0x1044 (LED MMIO).

### Solution
Added ADDI instruction sequences to construct full 16-bit address:

```systemverilog
LDI R1, #0x100        // Base = 0x100
ADDI R1, #0x100       // 0x100 + 0x100 = 0x200
ADDI R1, #0x100       // 0x200 + 0x100 = 0x300
// ... 15 iterations total ...
ADDI R1, #0x100       // 0xF00 + 0x100 = 0x1000
ADDI R1, #0x44        // 0x1000 + 0x44 = 0x1044 ✓
```

**Modified Sections**:
- Test 3: Lines 308-327 (LED Binary Counter Pattern)
- Test 4: Lines 362-395 (Negative Offset Addressing)
- Test 5: Lines 424-445, 456-458 (RAM/MMIO Boundary Test)

### Validation
✅ Test 3 PASSED - LED Binary Counter Pattern (4 patterns: 0x1→0x2→0x4→0x8)  
✅ Test 4 PASSED - Negative Offset Addressing (LED=0xFF)  
✅ Test 5 PASSED - RAM/MMIO Boundary Test (RAM[0xFF]=0x0F, LED[0x1044]=0x03)

## Bug #8: Scoreboard UVM_ERROR from Read-Only Registers

### Symptom
87 UVM_ERROR messages despite all tests passing:
```
UVM_ERROR: READ MISMATCH: ADDR=0x00001204 Expected=0x00000000 Got=0x00000301
```

### Root Cause
**File**: [sim/uvm/sv/axiuart_scoreboard.sv](../sim/uvm/sv/axiuart_scoreboard.sv)

Address 0x1204 = **REG_CPU_DBG_STATUS** (read-only status register)

```systemverilog
parameter bit [31:0] REG_CPU_DBG_STATUS = 32'h00001204;  // CPU debug status (RO)
```

This register returns computed CPU state (halted/running, break flags, etc.), not previously written data.

Scoreboard incorrectly verified read-only registers against `write_shadow_regs`:
1. CPU debug operations read REG_CPU_DBG_STATUS 87 times
2. Register returns computed status value (0x00000301)
3. Scoreboard compared against write shadow (no entry = 0x00000000)
4. **Result**: 87 READ MISMATCH errors

### Solution
Excluded read-only status/control registers from verification:

```systemverilog
// Exclude read-only status/control registers from verification
if (trans.address == axiuart_reg_pkg::REG_CPU_DBG_STATUS ||    // CPU debug status
    trans.address == axiuart_reg_pkg::REG_VERSION ||           // Hardware version
    trans.address == axiuart_reg_pkg::REG_TX_COUNT ||          // TX counter (RO)
    trans.address == axiuart_reg_pkg::REG_RX_COUNT ||          // RX counter (RO)
    trans.address == axiuart_reg_pkg::REG_FIFO_STAT ||         // FIFO status (RO)
    trans.address == axiuart_reg_pkg::REG_CPU_REG_DATA ||      // CPU regfile data
    trans.address == axiuart_reg_pkg::REG_CPU_TRACE_RDATA ||   // Trace buffer (RO)
    trans.address == axiuart_reg_pkg::REG_CPU_TRACE_PTR ||     // Trace pointer (RO)
    trans.address == axiuart_reg_pkg::REG_CPU_ID ||            // CPU ID (RO)
    trans.address == axiuart_reg_pkg::REG_REVISION) begin      // Revision (RO)
    // Just count the read without verification
    return;
end
```

**Modified File**: [sim/uvm/sv/axiuart_scoreboard.sv](../sim/uvm/sv/axiuart_scoreboard.sv) (Lines 140-179)

## Key Learnings

1. **Control Signal Separation**: Always separate read-latch operations from actual write operations to prevent unintended side effects.

2. **Address Construction**: TD4 CPU's 9-bit immediate limitation requires multi-instruction sequences (LDI + ADDI loops) to construct full 16-bit addresses.

3. **Verification Scope**: Scoreboards should verify only writeable registers. Read-only status registers return computed values and cannot be validated against write shadows.

4. **Debugging Workflow**:
   - Start with high-level symptoms (LED value incorrect)
   - Use waveforms to identify RTL-level issues (register corruption)
   - Trace through control signals to find root cause
   - Fix systematically and validate with comprehensive tests
